1. 결정과 이유

DECISION

검토한 토큰·부품·레이아웃을 폐쇄형 JSON 트리로 정의하고, 공통 검증기를 통과한 입력만 정적 HTML/CSS로 컴파일한다. 테마에 후보를 여러 개 두고, 구조·서체·밀도·반경을 독립 선택하게 한다.

에이전트가 ‘좋은 디자인’을 추측하는 범위를 줄인다. 문법과 접근성·출력 재현성은 강제하고, 미감의 최종 정답을 보증하지 않는다. 잘못된 지침은 반례를 통해 개정할 수 있게 버전·출처·회귀 검사를 남긴다.

4. 카탈로그와 실행 경로

재료 선택

시각 방향 → 팔레트 후보. 그 위에 셸 × 서체 × 밀도 × 반경을 독립 선택.

트리 조립

page의 첫 노드는 page-header 하나. section/grid의 허용 자식만 결합. 13노드 문법은 catalog 한 곳이 정본.

검증과 의미색

속성·깊이·개수·버전·URL·표 셀·필드 ID를 검사. 원본 팔레트는 보존하고 실제 배경에서 의미색 대비를 보정.

정적 코드와 일치 검사

HTML/CSS/토큰/manifest/입력 출력. check는 현재 compiler로 재컴파일해 추가·누락·수동 수정을 거부.

같은 compile API를 시각 조립기·CLI·CI가 공유한다. 에이전트 입력은 Blueprint로 한정한다.

7. 품질 게이트

  • 계약 테스트 먼저: 허용 입력 통과 + 금지 속성/간선/버전/URL/표/ID 실패.
  • 900개의 실제 사용 대비 쌍: 18팔레트 × 2모드 × 25쌍. 반올림 전 수치로 합격 판정.
  • 축의 조합 컴파일: 18 × 2 × 4 × 3 × 3 × 3 = 3,888개. 시각 품질 전수 검증을 뜻하지 않는다.
  • 재현 빌드: 새로운 임시 디렉터리와 버전 관리한 site 산출물을 바이트 단위로 비교.
  • 브라우저: 실제 선택·트리 편집·오류·복원·다운로드·모바일·키보드·폼을 실행하고 증거 저장.

8. 한계와 후속 결정

카탈로그도 틀릴 수 있는데?

미감의 정답이 아니라 개정 가능한 계약이다. 규칙 ID와 의도를 확인하고 재현 입력/화면 근거 → 반례 테스트 → 수정 → 버전/변경 로그 → 소비 lock 갱신으로 고친다.

정말 우회를 막을 수 있나?

compile API와 CLI 경계 안에서 임의 CSS/HTML을 막고, 생성물을 수동 수정하면 check가 실패한다. 검사기·CI 자체를 고칠 수 있는 쓰기 권한까지 막지 않는다. 소비 프로젝트의 보호 브랜치/필수 CI와 격리된 사용이 필요하다.

기존 디자인시스템을 바로 대체하나?

기존 브랜드 정본을 자동 대체하지 않는다. 버전 고정 수입·역할 매핑·허용 노드·대비 검증을 갖춘 어댑터는 후속 확장이다. 앱 비즈니스 동작과 서버 저장은 소비 프로젝트가 연결한다.

카카오 Katalog를 재현했나?

공개 검색과 if(kakao)26 공식 일정까지 확인했으나 정확한 발표/코드는 미확인이다. 사용자가 설명한 카탈로그·트리 조립 철학을 독립 설계에 참고한 것이며, 카카오 구현의 효과나 상세를 검증했다고 쓰지 않는다.

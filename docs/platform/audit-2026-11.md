## 0. 요약

1. **최신 조립 경로는 등록 자산의 일부만 쓴다.**
   - 경로: `assembleBlueprint` → `src/profiles/assemble.mjs`.
   - 템플릿 85개 중 11개, 테마 54개 중 25개, 2.6.0 컨트롤 10개 중 0개, 차트 프리셋 29개 중 2개만 쓴다.
   - 레시피 3개, 컨셉 17개, 구성 변형 슬롯 18개, 테마 변형은 쓰지 않는다.
2. **2.6.0 조립은 색과 서체의 다양성을 줄인다.** 이 경로가 만든 16,360개 조합을 모두 컴파일했다.
   - 색 토큰 집합은 light 1개, dark 1개뿐이다. 구형 경로에서는 테마마다 기본 팔레트를 쓰므로 light 토큰 집합이 54개다.
   - 실제로 적용되는 제목·본문 서체 짝은 3개뿐이다. 서체 축 값은 12개를 허용한다.
3. **등록 수량은 사용 가능 자산을 과장한다.**
   - 1,066개 중 257개는 한 팔레트를 한 함수가 펼친 파생 값이다. 427개는 권리를 확인하지 못한 Coolors 팔레트다.
   - 서로 다른 렌더 진입점은 28개다.
   - 속성 조합 795,799는 재료마다 속성 값의 곱을 더한 값이다. 금지 조합을 포함하고, 재료 사이의 조립 가능성과도 무관하다.
4. **조합 유효성은 따로 다루지 않는다.**
   - 프로파일은 속성마다 허용 목록만 둔다. 조합의 실패는 마지막 단계의 Blueprint 검증에서야 드러난다.
   - 실패 448건의 내역: 내비 규칙 위반 256건, 테마 금지와 프로파일 모드 충돌 192건.
5. **이름은 있지만 실제로 동작하지 않는 기능이 있다.**
   - `intent.components`는 검사만 하고 노드를 넣지 않는다.
   - 프로파일에 적힌 "추천" 차트 프리셋 7개 중 5개는 어떤 조합에서도 조립되지 않는다.
   - REST와 MCP에는 조립 기능이 없다.

## 3. 질문별 답과 호출 경로

### Q1. 구형 카탈로그 자산이 최신 assemble 경로에서 재사용되는가?

**부분적으로만 재사용된다. 색과 변형 계층은 재사용되지 않는다.**

호출 경로는 다음과 같다.

```text
service/assembleBlueprint  src/service/assemble.mjs:26
 → profiles/assemble        src/profiles/assemble.mjs:38
   → createBlueprint(pattern.template, themeId)   :105   ← layout·themeVariant·palette 옵션 없음
     → composeBlueprint     src/catalog/index.mjs:203  (테마 기본 축 + 템플릿 트리)
   → set('colorPalette', 'static-kit')            :110
   → set('typeRoles', p.type.rolePreset)          :115
 → compile → resolveTokens  src/tokens.mjs:39-43   ← colorPalette가 있으면 palettes[b.palette]를 읽지 않음
           → stylesheet     src/styles/index.mjs:82 ← renderRoleTypeCSS가 서체 변수를 덮음
```

| 재사용되는 것 | 재사용되지 않는 것 |
|---|---|
| 템플릿 트리 11개, 노드 렌더러, 축 값 표, 구성·페이지 규칙, 아이콘, 간격 | 팔레트(0/427), 테마 팔레트, 테마 변형, 구성 변형 18슬롯, 레시피, 컨셉, 템플릿 74개 |
| 테마 25개(축 기본값만) | 테마 29개, 2.6.0 컨트롤 8개 |

### Q2. 2.6.0 재료가 다양성을 축소하는가?

**그렇다. 색은 하나로, 서체는 셋으로 줄어든다.**

baseline이 프로파일·패턴의 허용값을 모두 펼쳐 16,808개를 조립했다. 그중 성공한 16,360개를 컴파일했다.

| 지표 | 2.6.0 조립 경로 | 비교: 구형 경로 |
|---|---:|---:|
| 서로 다른 색 토큰 집합 | light 1, dark 1 | 테마 기본 팔레트로 light 54 |
| 실제로 적용되는 서체 짝(마지막 `--kit-heading`·`--kit-font`) | 3 | 서체 프리셋 18 |
| 도달하는 테마 | 25 | 54 |
| 도달하는 템플릿 | 11 | 85 |

- 색: 프로파일 7개가 모두 `colorPalette: 'static-kit'` 하나만 허용한다(`src/profiles/data.mjs:91` 외 6곳). 그리고 `src/tokens.mjs:40`의 분기가 테마 팔레트를 건너뛴다.
- 서체: `renderRoleTypeCSS`가 `--kit-heading`에 역할형 프리셋 엔진의 서체를 쓴다(`src/materials/typography.mjs:186`). 이 CSS는 서체 축의 `typeVars` 뒤에 붙는다(`src/styles/index.mjs:82`).
- 실측: erp에서 `typography: 'mono'`를 골라도 최종 제목 서체는 system이다(baseline 측정 과정에서 확인).
- 바이트 단위로는 16,360개 출력이 모두 다르다. 그러나 차이는 밀도, 셸, 폭, 모서리 같은 축 값에서 나온다. 색과 서체 짝은 위 표의 수만큼만 있다.

### Q3. 등록 재료는 컴파일 가능한 코드인가, 메타데이터인가?

**재료마다 다르다. 등록 1,084개(designRegistry)는 아래와 같이 나뉜다.** 서로 다른 렌더 진입점은 28개다(baseline `materials.renderEntryPoints`).

| 판정 | 수 | 종류 |
|---|---:|---|
| 자기 구현이 있거나, 실제 함수가 읽는 데이터 자산 | 400 | 부품 65, 축 15, 아이콘 87, 템플릿 85, 테마 54, 차트 프리셋 29, 서체 프리셋 18, 페이지 유형 16, 패턴 11, 프로파일 7, 배치 원형 6, 역할형 4, 레시피 3 |
| 파생 값(한 함수가 계산한 값 하나) | 257 | color-token. 모두 `resolveColorTokens` 하나의 출력이다 |
| 권리 미확인 외부 자료 | 427 | palette(Coolors) |

400개 안에도 메타데이터 필드가 섞여 있다.

- 패턴의 `recipe`·`primitives`는 의존성 id로만 남는다(`src/profiles/registry.mjs:34`).
- 프로파일의 `pending`, 그리고 테마의 `palettes`(조립 경로에서 버려짐)도 같은 처지다.
- 레시피는 렌더 진입점이 `selectRecipe`로 되어 있지만 조립·컴파일 경로는 그 함수를 부르지 않는다.

**속성 조합 795,799는 조립 가능 조합이 아니다.**

- 재료마다 `variants` 값 개수를 곱해서 더한 값이다(`src/materials/contract.mjs:105`, `src/materials/registry.mjs:74`). 금지 조합을 포함한다.
- 실제로 조립·컴파일되는 조합은 16,360개다. 이것도 스칼라 축만 펼친 상한이다. 부품·차트 선택과 내용은 펼치지 않았다.

### Q4. 개별 속성 유효성과 조합 유효성이 구분되는가?

**최신 조립 경로에서는 구분되지 않는다.** 컨트롤 재료 안에서만 구분된다.

- **조립 경로**:
  - 각 속성 값이 허용 목록 안인지만 미리 본다(`src/profiles/assemble.mjs:69`에서 `:73`).
  - 조합이 맞는지는 마지막의 `validateBlueprint`에서야 알 수 있다(`:177`에서 `:182`, `ASSEMBLE_INVALID`).
  - 실패 448건은 모두 각 값은 허용되지만 함께 쓰면 안 되는 조합이다(baseline `failures`).
    - docs의 docs-reference + stacked·topbar 셸: 뼈대의 그룹 내비가 `NAV_GROUP`·`NAV_COUNT`에 걸린다.
    - saas-landing의 neon + light, docs의 civic + auto: 테마 금지와 프로파일 모드 허용이 충돌한다.
  - 진단 코드도 둘을 섞는다. 허용 목록 위반(`:72`)과 테마 금지 충돌(`:129`)이 같은 `ASSEMBLE_UNSUPPORTED`를 낸다.
- **컨트롤 재료**: 축 값 검사(`resolveProps`, `src/materials/control-kit.mjs:52`)와 금지 조합 검사(`violations`, `:49`)가 나뉘어 있다. 그러나 재료와 재료 사이(팔레트×서체×부품)의 조합 규칙은 없다.
- **플랫폼 계약**에서는 둘을 나눴다. 개별 속성은 `P_ATTR_*`(파이프라인 1에서 3단계)로, 조합은 `P_REL_*`와 `P_CHECK_*`(4단계와 6단계)로 보고한다. 이를 `tests/platform-minimal.test.mjs`의 "attribute validity and combination validity" 테스트가 검사한다.

### Q5. 추천 재료가 실제로 조립되는가?

**대부분 조립되지 않는다.**

- **차트 프리셋**:
  - 프로파일에 적힌 7개 중 조립되는 조합은 3쌍뿐이다.
    - erp/dashboard-grid/sales-pipeline-value
    - finance/dashboard-grid/finance-monthly-close
    - finance/dashboard-grid/sales-pipeline-value
  - erp-quarterly-revenue(stacked-bar), operations-activity-heatmap(heatmap), marketing-channel-share(donut), mobile-sparkline(sparkline)은 형태가 프로파일 `charts.kinds` 밖이다(`src/profiles/assemble.mjs:166`).
  - campaign-weekly-growth는 적용할 기본 차트가 없다(`:161`).
- **테마별 추천 팔레트**(`src/catalog/theme-palettes.mjs`)는 조립에서 쓰지 않는다.
- **레시피 추천**(`src/recipes.mjs:197`)은 갤러리와 workbench만 쓴다.
- **Studio**는 프로파일 조립을 `intent: {}`로만 부른다(`apps/web/features/studio/model.ts:169`). 그래서 Studio에서 나오는 조립 결과는 프로파일당 1개, 모두 7개뿐이다.
- **조립 경로의 "기본값"**은 관계나 근거로 고른 추천이 아니라 프로파일 목록의 첫 값이다(`src/profiles/data.mjs:69` 주석, `src/profiles/assemble.mjs:104`).

플랫폼 계약에서는 `selectMaterials`가 요구가 없을 때 `recommend()`의 1순위를 그대로 조립한다. 그래서 추천 1순위가 곧 조립 결과다. 이를 `tests/platform-minimal.test.mjs`의 "recommendation is the default assembly" 테스트가 검사한다.

### Q6. intent.components가 실제 삽입에 쓰이는가?

**쓰이지 않는다.**

- `src/profiles/assemble.mjs:76`에서 `:81`은 허용·대기·거부만 판정한다. 트리는 `:149`에서 `:156`처럼 슬롯 내용이나 뼈대만으로 만든다.
- 테스트가 이 동작을 고정한다: `tests/profiles-assemble.test.mjs:212` "component selection does not materialize a node".
- 실측: `assemble('erp', {components: ['data-table']})`는 `ok: true`이지만 트리에 data-table이 없다.

플랫폼 파이프라인의 `composeComponents`는 `intent.components`를 하나씩 패밀리 구성원으로 렌더해 넣는다. 테스트는 넣은 article 수가 요청 수와 같은지 본다.

### Q7. REST/MCP가 같은 조립을 쓰는가?

**REST와 MCP에는 조립이 없다.** 검증과 컴파일만 같은 서비스 함수를 쓴다.

- MCP 도구는 6개다: list_design_system, get_design_schema, get_component_spec, validate_blueprint, compile_design, explain_design_decisions(`apps/web/lib/api/mcp.mjs:30`에서 `:69`).
- REST 연산은 `assembleBlueprint`를 import하지 않는다(`apps/web/lib/api/operations.mjs:3`). 경로는 `apps/web/app/api/v1/`의 catalog, compile, components, explain, schema, themes, validate다.
- `assembleBlueprint`를 부르는 곳은 브라우저 Studio(`apps/web/features/studio/model.ts:169`)뿐이다.
- 따라서 외부 에이전트는 조립을 하지 못한다. 템플릿을 직접 만들어 검증과 컴파일만 할 수 있다.
- 조립 엔진 작업은 서비스 함수 하나(`assembleDesign`)를 만들고, REST와 MCP가 그 함수를 함께 부르게 한다(ADR 0012 §7, wbs W5).

## 5. 웹 문제(Core 관점에서만)

- Studio의 프로파일 조립은 `intent: {}`만 넘긴다(`apps/web/features/studio/model.ts:169`). Core에는 이미 축 요구를 받는 경로가 있지만 웹이 그것을 쓰지 않는다.
- Core에는 최상위 필드(`colorPalette`, `typeRoles`)를 바꾸는 편집 연산이 없다(`docs/materials/audit.md` §7의 2번). 그래서 웹은 문서를 통째로 바꿔야 한다.
- REST와 MCP에 조립이 없다는 것은 Core 서비스에 공개 함수가 없다는 뜻이기도 하다. 웹 작업이 아니라 조립 엔진 작업(W5)의 몫이다.

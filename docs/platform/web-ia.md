# 웹 개편 설계안: 디자인 탐색·재료 조합·코드 조립 플랫폼

근거는 `docs/platform/web-audit.md`다. 문제 ID(H1, M2, S6 등)는 그 문서의 번호다.

이 문서는 `docs/adr/0010-assembly-platform.md`(작성 중, 이 시점에 없음)의 Core 계약이 생긴다고 가정한다. 가정한 계약은 다섯 가지다.

1. 팔레트와 서브토큰 세트는 다대다다.
2. 타이포 시스템은 팔레트와 독립이다.
3. 컴포넌트는 디자인 패밀리를 가진다.
4. 재료 사이에 관계와 추천 모델이 있다.
5. 조립 파이프라인이 있다.

데이터 인터페이스는 7절에서 추상 모양으로만 적는다. 이름과 필드는 ADR이 확정되면 바꾼다.

## 1. 원칙

| 원칙 | 의미 |
|---|---|
| 먼저 보여 주고 나중에 설명한다 | 모든 화면의 첫 화면은 실제 렌더 결과다. 규약, 진단 코드, 토큰 이름은 접힌 "자세히"나 Docs로 보낸다(H1, H2, C2). |
| 비교가 기본 동작이다 | 팔레트, 타이포, 패밀리, 디자인 후보 모두 2~4개를 한 화면에 놓는다(MC1, MT1, E2, S3). |
| 되는 것만 눌리게 한다 | 호환되지 않는 선택은 누르기 전에 비활성으로 두고 사람 말 이유를 붙인다. 진단 코드는 보조 텍스트다(MF1, C5). |
| 바꾸기 전에 영향을 보여 준다 | 사용자가 고친 내용이 있는 문서를 바꿀 때는 적용 전에 영향 요약을 보여 준다(S6, R3). |
| 화면에 반영되지 않는 선택지는 두지 않는다 | 출력에 영향이 없는 선택지는 숨기거나 "메타데이터만 저장됨"이라고 명시한다(R1, R2). |
| 주소가 상태를 말한다 | 보고 있는 재료, 비교 대상, 기기 폭, 단계가 주소에 있어 새로고침, 뒤로 가기, 공유가 같은 화면을 연다(B5, B8, B10). |

## 2. 라우트 구조

현재 6개 메뉴(Explore, Materials, Components, Docs, Integrations, Studio)를 만드는 쪽(Explore, Materials, Components, Studio)과 아는 쪽(Docs)으로 나눈다. Integrations는 Docs 안으로 들어간다(D1).

```
/                                   Home
/explore                            디자인 둘러보기(필터, 후보 담기)
/explore/[designId]                 디자인 상세(재료 바꿔 보기, Studio로 이어가기)
/materials                          재료 허브(색, 타이포, 기초 재료, 관계 보기)
/materials/palettes                 팔레트 목록
/materials/palettes/[paletteId]     팔레트 상세: 서브토큰 세트 시각 비교
/materials/typography               타이포 시스템 목록과 같은 문장 비교
/materials/typography/[systemId]    타이포 시스템 상세
/materials/foundations              기초 재료 허브(현재와 같음)
/materials/foundations/[axis]       축 상세(현재와 같음, 값 비교 추가)
/components                         패밀리 중심 목록
/components/families/[familyId]     패밀리 비교(같은 부품을 패밀리별로)
/components/[componentId]           부품 상세(상태, 크기, 기기, 내보내기)
/studio                             Studio 시작(단계 1)
/studio/[draftId]                   작업 중 문서(단계 2~6)
/docs                               가이드와 레퍼런스
/docs/guide/[slug]                  시작 가이드
/docs/core/[slug]                   Core 레퍼런스(Blueprint, 카탈로그, 규칙, 한계)
/docs/integrations                  연동 개요
/docs/integrations/{cli,rest-api,mcp}   현재 /integrations/* 가 옮겨 온다
```

기존 주소는 308 리다이렉트로 보존한다.

| 기존 | 새 위치 |
|---|---|
| `/integrations`, `/integrations/cli`, `/integrations/rest-api`, `/integrations/mcp` | `/docs/integrations/...` |
| `/docs/getting-started` 등 | `/docs/guide/...` 또는 `/docs/core/...` |
| `/materials/color` | `/materials/palettes` (쿼리 보존) |
| `/studio?...` 시작 인자 | 그대로 유효. 새 인자는 추가만 한다 |

`/dev/qa/combos`의 조합 격자와 품질 등급 화면은 Explore의 "품질" 필터로 흡수한다(4절 Explore). 내부 QA 주소는 유지한다.

상단 메뉴는 `Explore · Materials · Components · Studio · Docs` 5개다. Docs는 오른쪽 끝 보조 링크로 둔다. GitHub 링크는 푸터에 그대로다.

```

#### 팔레트 상세: 서브토큰 세트 시각 비교 `/materials/palettes/[paletteId]`

팔레트와 서브토큰 세트가 다대다이므로 "팔레트를 고르면 쓸 수 있는 서브토큰 세트가 나열되고, 세트를 바꾸면 같은 샘플이 다시 그려진다"를 기본 화면으로 한다.

```
팔레트: [ Static Kit ▾ ]   모드 ( 라이트 | 다크 | 나란히 )   비교 대상 [+ 팔레트 추가]
┌ 원본 색(시드) ─────────────────────────────────────────────────────┐
│ ● brand ● neutral ● aux ● success ● warning ● danger ● info         │
└────────────────────────────────────────────────────────────────────┘
서브토큰 세트   ( ◉ 기본 )  ( ○ 부드러움 )  ( ○ 고대비 )  ( ○ 모노 )   ← 이 팔레트와 호환되는 세트만
┌ 같은 샘플 화면 × 세트별 ───────────────────────────────────────────┐
│ ┌ 기본 ─────────┐ ┌ 부드러움 ─────┐ ┌ 고대비 ───────┐ ┌ 모노 ─────┐ │
│ │ [버튼] 카드   │ │ [버튼] 카드   │ │ [버튼] 카드   │ │ ...       │ │
│ │ 입력 표 알림  │ │ 입력 표 알림  │ │ 입력 표 알림  │ │           │ │
│ │ 대비 AA 통과  │ │ 대비 AA 통과  │ │ 대비 AAA      │ │ 대비 AA   │ │
│ └───────────────┘ └───────────────┘ └───────────────┘ └───────────┘ │
└────────────────────────────────────────────────────────────────────┘
▸ 서브토큰 상세(접힘): 역할 색 / 상태 색 / 부품 색 표 · CSS·JSON 내보내기
▸ 어울리는 글자 시스템 (추천 이유):  [ ERP ] 정보 밀도가 높은 화면에 맞음 …
[이 조합으로 Studio 열기]   [이 팔레트를 비교에 담기]
```

- 샘플 화면은 고정된 "재료 시험대" 한 장(버튼, 카드, 입력, 표, 상태 알림, 차트 조각)을 서브토큰 세트별로 렌더한다. 현재 `ModeCompare`의 장면을 시험대로 확장한다.
- 세트가 팔레트와 호환되지 않으면 칩이 비활성이고 이유 한 줄을 보인다(예 "이 팔레트의 중립색이 고대비 세트의 기준을 못 맞춤"). 코드는 툴팁으로 내린다.
- 토큰 표(`ColorExplorer`)는 "서브토큰 상세" 접이식 안으로 옮겨 본문 길이를 줄인다(MC2, 모바일 14,172px).
- 비교는 팔레트 2~3개를 나란히 놓는 모드를 제공한다. 같은 시험대를 팔레트별로 그린다.
- 모바일: 세트 비교는 가로 스크롤 카드 대신 세트 칩 + 한 장씩 보기로 바꾼다. "나란히"는 데스크톱 전용이다.

┌ 역할: 제목 ───────────────────────────────────────────────────────┐

- 같은 실제 텍스트를 시스템별 줄로 쌓아 비교한다(MT1). 사용자 입력 문구(MT2)는 `?text=` 쿼리로 공유한다.
- 화면 폭 토글로 같은 문장이 390에서 줄바꿈이 어떻게 되는지 본다. 현재 `Sample` 컴포넌트의 줄바꿈 정책 처리를 그대로 쓴다.
- 타이포는 팔레트와 독립이므로 이 화면은 팔레트 선택을 요구하지 않는다. 하단 "어울리는 팔레트"는 추천일 뿐 제약이 아니다.

#### 호환 재료와 추천 이유

모든 재료 상세의 하단에 같은 모양의 "어울리는 재료" 블록을 둔다.

```
어울리는 재료
 ┌─────────────┬──────────────┬────────────────────────────────┐
 │ 재료        │ 상태         │ 이유                           │
 ├─────────────┼──────────────┼────────────────────────────────┤
 │ 글자 ERP    │ 추천         │ 정보 밀도 높음 · 이 팔레트의 중립색 대비 충분 │
 │ 글자 Doc    │ 가능         │ …                              │
 │ 모서리 round│ 쓸 수 없음   │ 이 테마와 충돌 (자세히: AXIS_BAN) │
 └─────────────┴──────────────┴────────────────────────────────┘
```

상태 세 가지(추천, 가능, 쓸 수 없음)와 이유 문장은 `relations()`와 `recommend()`가 준다(7절). 쓸 수 없는 재료는 숨기지 않고 이유와 함께 남겨 사용자가 한계를 안다.

### 3.3 Components

#### 목록 `/components` (패밀리 중심)

```
Components        보기 ( 패밀리 | 역할별 )     검색 [        ]
패밀리: 기본 · 소프트 · 아웃라인 · 글래스 ...   ← 칩, 눌러서 전체 부품 미리보기가 패밀리로 바뀜
┌ 버튼 ───────┐ ┌ 입력 ───────┐ ┌ 카드 ───────┐ ┌ 표 ──────────┐
│ [렌더]      │ │ [렌더]      │ │ [렌더]      │ │ [렌더]       │
│ 변형 6 · 3 패밀리 │ ...
└─────────────┘
```

- 패밀리 칩을 누르면 모든 카드의 썸네일이 그 패밀리로 다시 그려진다. 부품 간 통일감을 한눈에 본다.
- 카드 메타는 "변형 N · 패밀리 M"만 보여 준다. `type`, `since`, `kind`, `category`, 맥락 같은 내부 값은 상세의 "정보" 탭으로 보낸다(C1).
- 기존 구조 그룹(페이지 구조, 콘텐츠 등)은 "역할별" 보기로 남긴다.

#### 패밀리 비교 `/components/families/[familyId]?with=outline,glass`

```
패밀리 비교   기본 | 소프트 | 아웃라인 | 글래스     부품 [버튼 ▾]   상태 [전체 ▾]   크기 [전체 ▾]
        │ 기본      │ 소프트    │ 아웃라인   │ 글래스
────────┼───────────┼───────────┼────────────┼──────────
 기본   │ [저장]    │ [저장]    │ [저장]     │ [저장]
 hover  │ [저장]    │ [저장]    │ [저장]     │ [저장]
 pressed│ ...
 loading│ ...
 disabled│ ...
```

- 행은 상태, 열은 패밀리다. 크기는 필터로 바꾸거나 "크기 전체"로 열 안에 세로로 쌓는다.
- 한 부품을 패밀리 2~4개로 비교하는 용도다. 현재 부품 상세의 select로 하나씩 보는 방식(C4)을 대체한다.

│                                              │  │ behavior    ( action toggle ) │
│                                              │  │ state       ( … )        │
└──────────────────────────────────────────────┘  │ ⚠ pressed는 toggle에서만  │
                                                   │   → [behavior를 toggle로] │
탭:  사용법 | 상태·크기 | 코드 | 규약(Docs 링크) | 정보
```

- 금지 조합 사전 반영: 선택 패널은 현재 선택을 기준으로 각 값의 가능 여부를 계산한다. 불가능한 값은 비활성이고 이유 한 줄과 "함께 바꾸기" 단추가 붙는다(C5). 판정 함수는 `edit/applicability`의 선택 가능성 판정과 같은 모양의 부품용 질의를 Core에서 받는다(7절 `choices()`).
- 상태·크기 탭: 모든 상태 × 크기 격자를 한 화면에 그린다(C4).
- 기기: 데스크톱과 모바일을 나란히 그린다. 현재 2.6.0 부품에만 있는 "넓게/좁게 375px" 토글(`ComponentPreview.tsx:61-64`)을 모든 부품으로 넓힌다(C3).
- 코드 탭과 내보내기 메뉴(C6): `HTML+CSS 조각`, `Blueprint JSON 노드`, `Studio에서 열기`. 선택한 패밀리, 크기, 상태를 반영한다. 복사는 `CopyBlock`을 쓴다.
- 규약(허용 속성 표, 허용 부모·자식, 제약 코드, 적용 토큰)은 "규약" 탭으로 내리고 기본 탭은 사용법과 미리보기다(C2). 같은 내용을 `/docs/core/components`에도 둔다.

### 3.4 Studio

#### 흐름: 페이지 유형 → 디자인 방향 → 후보 비교 → 재료 교체 → 콘텐츠 수정 → 내보내기

6단계 진행 막대를 상단에 둔다. 단계는 주소에 있다(`/studio/[draftId]?step=compare`). 뒤로 가기는 단계 사이를 오간다.

```
① 페이지 유형  ② 디자인 방향  ③ 후보 비교  ④ 재료 교체  ⑤ 콘텐츠  ⑥ 내보내기
━━━━━━━━━━●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**① 페이지 유형** (`/studio`)

```
무엇을 만들까요?
[랜딩] [대시보드] [문서] [폼] [목록·탐색] [협업] [글] [설정] ...    각 칸에 실제 썸네일
또는  [JSON 가져오기]  [이어서 작업: 쇼핑몰 랜딩 (수정됨, 2시간 전)]
```

- 시작 버튼 4개와 "2.6.0"(`StartScreen.tsx:19-28`)을 없애고 페이지 유형을 고른다(S1). "Design Profile"은 ②에서 "방향 프리셋"으로 나온다.
- 작업 중인 문서가 있으면 이어서 작업하기가 맨 앞에 선다.

**② 디자인 방향**

```
방향을 고르세요  (선택한 유형: 랜딩)
[신뢰감 있는 SaaS] [따뜻한 카페] [럭셔리] [대담한 네온] ...    각 칸: 렌더 + 한 줄 설명
고급: 직접 고르기 ▸ 테마 · 팔레트 · 글자 · 모서리
```

- 방향은 `recommend({pageType})`가 준 후보다. 각 후보는 테마, 팔레트, 서브토큰 세트, 글자 시스템, 패밀리를 묶은 값이다.

**③ 후보 비교**

```
후보 3개 (최대 4)   [+ 후보 추가]                               기기 ( 390 | 1280 | 나란히 )
┌ A 신뢰감 ───────┐ ┌ B 따뜻함 ───────┐ ┌ C 대담함 ───────┐
│ (실제 렌더)     │ │ (실제 렌더)     │ │ (실제 렌더)     │
│ 팔레트·글자·패밀리│ │ ...             │ │ ...             │
│ [이걸로 계속]   │ │ [이걸로 계속]   │ │ [이걸로 계속]   │
└─────────────────┘ └─────────────────┘ └─────────────────┘
```

- 후보는 같은 콘텐츠에 재료 묶음만 다르게 적용한 문서들이다. 선택한 후보 하나가 `draft`가 되고 나머지는 "후보 보관함"에 남아 ④에서 다시 꺼낼 수 있다(S3).
- 같은 템플릿과 콘텐츠로 비교한다. 후보 렌더는 서버가 아니라 브라우저에서 Core로 컴파일한다(현재 Studio와 같은 경로).

**④ 재료 교체** (현재 디자인 탭을 대체)

```
┌ 재료 ─────────────────────┐  ┌ 미리보기 (기기 토글) ─────────────────┐
│ 팔레트   ● Static Kit  [바꾸기] │  │                                       │
│ 세트     기본          [바꾸기] │  │   실제 렌더                           │
│ 글자     ERP           [바꾸기] │  │                                       │
│ 패밀리   소프트        [바꾸기] │  └───────────────────────────────────────┘
│ 모서리·간격 …          [바꾸기] │  변경 영향: 바뀌는 곳 3 · 내가 고친 곳 0 · 유실 0
└───────────────────────────┘
```

- "바꾸기"는 오른쪽 패널을 후보 격자로 연다. 후보 위에 마우스를 올리면 미리보기가 임시로 바뀌고, 누르면 적용한다.
- 각 후보에는 "추천/가능/쓸 수 없음 + 이유"가 붙는다(3.2 호환 재료 블록과 같다).
- 미리보기에 반영되지 않는 선택지는 만들지 않는다(R1~R3). Design Profile은 ②의 방향 프리셋으로 올려 문서를 실제로 조립하는 결과(`assemble`)로만 쓰고, 도중에 바꾸는 select로는 두지 않는다.
- 2.6.0 문서 업그레이드가 필요한 재료를 고르면 적용 전에 영향 요약을 보여 준다(아래).

**⑤ 콘텐츠 수정**

```
┌ 구조 ─────────────┐ ┌ 미리보기: 눌러서 선택 ─────────────┐ ┌ 속성 ────────┐
│ 페이지            │ │  [히어로] ← 클릭하면 왼쪽·오른쪽  │ │ 제목  [    ] │
│  ├ 히어로         │ │  동기화                            │ │ 본문  [    ] │
│  ├ 로고 모음      │ └─────────────────────────────────────┘ │ 버튼  [    ] │
│  └ 섹션 …         │                                          └──────────────┘
└───────────────────┘
```

- 현재 구조 트리와 필드 폼(`StructurePanel`, `NodeForm`)을 그대로 쓰고, 미리보기에서 요소를 눌러 선택하는 연결을 더한다(S7). 미리보기가 `sandbox=""`라 스크립트를 못 쓰므로, 컴파일 결과에 노드 경로 `data-path`를 심고 iframe 위에 투명 선택 층을 두는 방식을 쓴다(구현 방식은 Core의 `data-*` 출력 계약 확인 필요).
- 콘텐츠를 고친 필드는 `userEdited` 경로 집합에 기록된다(영향 표시의 근거).

**⑥ 내보내기**

```
내보내기
 ( ◉ HTML 파일 )  ( ○ HTML+CSS+토큰 묶음 .zip )  ( ○ Blueprint JSON )  ( ○ 코드 조각 복사 )
 검사 결과: 접근성 대비 통과 · 규칙 위반 0 · 경고 2 [자세히]
 [내려받기]    링크로 공유 [링크 만들기]
```

- 검사 결과는 `validate`/`compile`의 결과와 `manifest`의 대비 기록에서 읽는다. "왜 이렇게 됐나" 보기는 `explainDecisions`로 만든다(4.4의 미노출 기능).

#### 사용자 편집 덮어쓰기 전 영향 표시

적용할 변경(재료 교체, 템플릿 교체, 방향 프리셋 교체, 주소 시작 요청, JSON 가져오기)마다 같은 대화상자를 쓴다. 현재 확인창(`Dialogs.tsx:31-43`)을 대체한다(S6).

```
"소프트 패밀리"로 바꿀까요?
 ┌ 영향 요약 ──────────────────────────────────────────────┐
 │ 바뀌는 값            4   모서리, 그림자, 버튼 패밀리, ... │
 │ 내가 고친 내용        2   히어로 제목, 버튼 문구 → 유지됨 │
 │ 유지할 수 없는 선택   1   모서리=square → 새 패밀리에서 쓸 수 없어 기본값 │
 │ 콘텐츠 유실           0                                   │
 └─────────────────────────────────────────────────────────┘
 ▸ 자세히 (필드별 전/후)     [취소]   [적용]   (실행 취소로 되돌릴 수 있음)
```

- 판정은 문서 쪽에서 계산한다: `impact(doc, change)`가 변경 전/후 문서의 `diffDocs`(바뀌는 값)와 `contentDiff`(콘텐츠 유실)를 비교하고, Studio가 가진 `baseline`(최초 상태)과 `diffDocs(baseline, doc)`로 "내가 고친 곳"을 정한다. `diffDocs`, `contentDiff`는 지금 웹이 쓰지 않는 Core 함수다(4.4).
- 영향이 전부 0이면 확인 없이 바로 적용하고 "실행 취소" 토스트만 띄운다. 현재 `isDisposable`(`protect.ts:9`)의 "버려도 되는 문서" 판정은 유지한다.
- R3(구 문서의 조용한 2.6.0 승급)은 "문서 버전이 올라가고 색이 바뀝니다"를 영향 행으로 보여 준다.

#### 주소와 저장

| 상태 | 위치 | 이유 |
|---|---|---|
| 단계, 탭, 패널 배치, 기기 폭, 색 보기, 배율 | 주소 쿼리 | 새로고침, 공유, 뒤로 가기에서 같은 화면(B5) |
| 문서 | 브라우저 저장소(`draftId`별) + 공유용 링크 | 현재 키 하나(`winterholic-static-kit.studio.v1`)를 draft 여러 개로 확장 |
| 실행 취소 기록 | 메모리 + 저장소에 최근 N단계 | 새로고침 뒤에도 되돌리기(B7) |
| 후보 보관함 | 문서와 같은 draft | 비교 단계의 후보 보존 |

- 문서 공유(B8): 백엔드 없이 하려면 Blueprint를 압축해 `#d=` 해시에 담는 방식이 있고(크기 한계 확인 필요), 서버 저장이 필요하면 별도 결정이다. 이 설계안은 해시 방식을 기본으로 가정하고 서버 저장은 열어 둔다.
- 뒤로 가기(B10, B11): 편집마다 history가 늘지 않도록 미리보기 iframe 갱신 방식을 바꾼다. 후보는 iframe 요소를 `key`로 교체하거나 `contentDocument.open/write`를 쓰는 방법이 있다. 어느 쪽이 항목을 안 늘리는지는 구현자가 Chromium, Firefox, WebKit에서 `history.length`로 확인해야 한다(확인 필요). 단계 전환만 `pushState`, 나머지 뷰 변경은 `replaceState`로 한다.
- 모바일 기본 기기 폭은 화면 폭에 맞춰 390으로 연다(S4). 툴바는 한 줄로 줄이고 "되돌리기/다시"만 상시 노출, 나머지는 더보기로 보낸다(S5).

## 4. 상태 관리 방식

세 층으로 나눈다.

| 층 | 무엇 | 어디에 둠 | 비고 |
|---|---|---|---|
| 서버 데이터 | 재료, 관계, 추천, 카탈로그, 시험대 렌더 | 서버 컴포넌트가 Core 질의를 읽어 정적 생성(`generateStaticParams`) | 지금 Materials, Components, Explore가 쓰는 방식 그대로(`materials.server.ts`, `spec.server.ts`, `designs.server.ts`) |
| 화면 상태 | 비교 대상, 선택한 패밀리·상태·기기, 단계 | URL 쿼리(`?with=`, `?state=`, `?device=`, `?step=`) | 서버 컴포넌트가 쿼리를 읽어 첫 렌더를 만들고, 클라이언트 컨트롤은 `router.replace`로 쿼리만 바꾼다. `typography/page.tsx:26`의 `?preset=`과 `explore/list-query.ts`가 이미 쓰는 방식이다 |
| 작업 상태 | Studio draft, 후보 보관함, 실행 취소 기록, 저장 상태 | 클라이언트 리듀서 + 저장소 | 현재 `features/studio/model.ts`의 3층(문서, 세션, 뷰)을 유지한다. 다시 쓰지 않고 확장한다 |

Studio 리듀서 확장 지점:

- `Snapshot`에 `userEdited: string[]`(경로 목록)과 `candidates: Draft[]`를 더한다. 순수 리듀서 구조는 그대로다.
- `Intent`에 `swapMaterial`, `applyCandidate`, `applyDirection`을 추가한다. 각 의도는 `perform()`이 Core 연산과 `impact()`를 함께 부른다.
- `needsConfirm`(`model.ts:403`)은 불리언이 아니라 `ImpactReport`를 돌려주게 바꾼다. 영향이 0이면 `null`이다.
- 저장은 지금처럼 `peekSaved`, `mayOverwriteStored`(`protect.ts:12-16`)로 다른 탭 덮어쓰기를 막는다. 키만 draft별로 나눈다.

Materials와 Components의 비교 화면은 서버 상태가 아니라 쿼리가 진실이다. 클라이언트 전역 저장소는 쓰지 않는다. 후보 담기 목록(Explore)만 예외로 `localStorage`의 짧은 목록(최대 4개)을 쓴다.

## 7. 데이터 인터페이스(추상)

ADR 0010이 확정되면 이름과 필드를 바꾼다. 화면은 아래 모양만 가정한다. 모든 함수는 Core 서비스 봉투(`{ok, value|errors, warnings}`)를 그대로 쓰고 던지지 않는다. 읽기 전용 질의는 서버 컴포넌트에서, 편집·영향 계산은 브라우저에서 같은 순수 함수로 부른다.

```ts
// 재료 그래프: Materials, Explore 상세, Studio ④가 쓴다
listMaterials({kind, filter?, query?}): Material[]          // kind: palette | subtokenSet | typeSystem | family | axis ...
getMaterial({id}): Material & {preview: PreviewSpec}         // preview: 시험대 렌더에 필요한 최소 정보
relations({id, kinds?}): Relation[]
  // Relation = {target: MaterialRef, status: 'recommended'|'compatible'|'blocked',
  //             reason: {text: string, code?: string}}     // text는 사람 말, code는 진단 코드(보조)
recommend({pageType?, direction?, with?: MaterialRef[]}): Recommendation[]
  // Recommendation = {materials: MaterialRef[], why: string[], score?: number}

// 선택 가능성: 부품 상세와 Studio가 쓴다
choices({subject: ComponentRef | Document, current: Selection}): Choice[]
  // Choice = {axis, value, ok: boolean, reason?: {text, code}, fixWith?: Selection}

// 조립 파이프라인: Studio ②~⑥이 쓴다
plan({pageType}): Direction[]                                // 방향 프리셋 목록(재료 묶음 + 설명)
assemble({pageType, direction, content?, overrides?}): {document, manifest}
swap({document, material: MaterialRef}): {document, impact: ImpactReport}
impact({document, change, baseline}): ImpactReport
  // ImpactReport = {changed: FieldChange[], userEdits: PathChange[],
  //                 unsupported: {selection, reason}[], contentLoss: number, versionBump?: {from, to}}
export({document, target: 'html'|'bundle'|'json'|'snippet', selection?}): {files: File[], checks: CheckSummary}
explain({document|manifest, path?}): Decision[]              // 현재 explainDecisions
```

대응 관계(현재 Core 기능 → 화면에서의 쓰임):

| 현재 | 새 역할 |
|---|---|
| `src/edit/applicability.mjs`의 `*Choices` | `choices()`의 문서 쪽 구현 |
| `diffDocs`, `contentDiff`, `keepsContent` | `impact()`의 바뀌는 값과 콘텐츠 유실 판정 |
| `assembleBlueprint`, `src/profiles/assemble.mjs` | `assemble()`의 방향 프리셋 구현 |
| `src/materials/registry.mjs`의 `search`, `filter`, `dependencies` | `listMaterials()`, `relations()`의 바탕 |
| `compileBlueprint`의 `manifest` | `export()`의 검사 요약, `explain()` |

화면이 Core 값을 UI에 복제하지 않는다는 현재 원칙(`apps/web/AGENTS.md`)은 그대로다. 추천 이유와 비활성 이유의 사람 말은 Core가 준 `reason.text`를 그대로 쓰고 웹에서 새로 쓰지 않는다. 문구가 필요하면 Core 힌트(`HINTS`)에 추가한다.

## 8. 구현 순서 제안

선행 의존이 적은 것부터 쌓는다. 각 단계는 독립적으로 배포 가능하다.

| 순서 | 범위 | 이유 |
|---|---|---|
| 1 | 반영 결함 제거(R1~R3), history 항목 늘어남(B10), 모바일 기본 기기 폭(S4) | Core 계약 없이 가능하고 신뢰를 해친다 |
| 2 | Docs 분리와 Home 메시지 교체, 메뉴 5개 | 문구와 라우트만 바꾼다 |
| 3 | 영향 요약 대화상자(`diffDocs`, `contentDiff` 사용) | Core 함수가 이미 있다 |
| 4 | Components 상세 재구성(탭, 기기 나란히, 상태×크기, 내보내기) | 패밀리 없이도 가능. 패밀리 열은 계약 뒤에 추가 |
| 5 | Materials 비교 화면(팔레트 세트, 타이포 같은 문장) | ADR 0010의 다대다·독립 타이포 계약 필요 |
| 6 | Studio 단계 흐름, 후보 비교, 재료 교체 | `plan`, `assemble`, `recommend` 필요 |
| 7 | Explore 후보 담기와 비교 | Studio ③과 같은 부품이라 6 다음 |

검증은 기존 Playwright 스위트(`apps/web/e2e/`)에 반영 시험(재료를 바꾸면 미리보기 해시가 바뀐다, 안 바뀌면 선택지가 없다)을 추가한다. `studio-probe.mjs`, `color-probe.mjs`의 방식이 그대로 시험이 된다.

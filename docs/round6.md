# 6차 개선 기록: 전체 조합 갤러리 (2026-10-20~21)

목표는 하나다. **템플릿 × 구성 변형 4,102가지를 배포 사이트에서 하나하나 훑어보고**, 편차가 큰(이상한) 조합을 사용자가 직접 눈으로 찾아 표시할 수 있게 한다. 표시한 목록은 다음 품질 개선의 입력이다.

진입은 조립기 메뉴의 **전체 조합**, 주소는 `/combos/`다.

## 1. 설계 결정: 파일로 만들지 않고 브라우저에서 즉석 컴파일

4,102개 정적 HTML을 만들어 커밋·업로드하는 방식은 택하지 않았다. 5차에서 test-lab을 3,380쪽에서 2,102쪽으로 줄인 이유(커밋 용량 172MB → 102MB, Vercel 업로드 한도)가 그대로 재발한다. 컴파일된 페이지는 중앙값 약 66KB, 최대 약 91KB이므로 4,102쪽은 약 270MB다.

대신 조립기가 이미 브라우저에서 돌리는 컴파일러(`src/catalog.mjs`·`src/compiler.mjs`)를 그대로 쓴다. 한 조합을 만드는 데 드는 시간이 매우 짧아(검증·컴파일 포함 약 1ms, Node) 가능한 방식이었다. 추가 배포물은 `combos/` 두 파일과 소스 몇 개뿐이다(생성 파일 +6개, 2,851 → 2,857).

| 파일 | 역할 |
|---|---|
| `src/combos.mjs` | 순수 로직. 조합 열거·id·필터·정렬·렌더·내보내기 글. Node(시험)와 브라우저가 같은 코드를 쓴다 |
| `src/combos/app.mjs`, `src/combos.css` | 갤러리·확대 보기·이상함 목록 화면 |
| `combos/index.html` | 갤러리 + 확대 보기(`<dialog>`) |
| `combos/render.html`, `src/combos/render.mjs` | 한 조합을 화면 전체에 그대로 그리는 주소(새 창·폰 실제 폭 확인용) |

### 조합이란

한 조합 = 템플릿 하나 + 구성 변형 슬롯마다 {기본 | 옵션 하나}를 고른 것이다. 템플릿마다 슬롯 선택지 수 (옵션 + 1)의 곱을 구해 85개를 더하면 **4,102**이고 `node scripts/audit.mjs`의 `4,102 template×layout compositions`와 같다(`tests/combos.test.mjs`가 같은 계산으로 확인한다). 테마·테마 변형·팔레트·모드는 조합이 아니라 **보기 설정**이다. 어느 조합이든 54개 테마 × 427개 팔레트 × 라이트/다크로 바꿔 볼 수 있다.

- **id**: `템플릿~슬롯:옵션~슬롯:옵션`(슬롯 순서는 고정, 기본 구성은 템플릿 id만). 예 `saas-landing~hero:product~cards:outline`. 공유·기록은 이 id를 쓴다.
- **번호**(`#0001`~`#4102`): 목록 순서이며 카탈로그가 바뀌면 달라질 수 있다. 화면에는 보이지만 기록의 기준은 id다.
- **같은 화면(120개)**: 앞 슬롯의 변경이 뒤 슬롯의 조건을 없애 서로 다른 선택이 같은 화면이 되는 경우다. 이를 숨기지 않고 "#N과 같은 화면" 표시와 "같은 화면 숨기기" 필터로 구분했다. 이것은 구성 변형 설계의 한계이기도 하므로 다음 개선 후보다. 실제로 서로 다른 화면은 3,982개다.

## 2. 화면과 동작

**갤러리**

- 4,102개 전부를 번호·이름·변형 요약과 함께 쪽 단위(24/48/96)로 나열한다. 쪽 이동, 쪽 번호 입력.
- 검색(번호·id·템플릿 이름·페이지 유형·슬롯·옵션 이름, 낱말 AND), 페이지 유형, 템플릿, **슬롯별 필터**(16종 슬롯, 선택지 35개, 개수 표시), 같은 화면 숨기기, 이상함만 보기.
- 정렬: 템플릿 순 · **바꾼 슬롯 많은 순**(편차 큰 조합이 앞에 온다) · 섞기. 모든 필터·쪽·정렬이 주소에 들어가 새로 고침과 공유에 살아남는다.
- **썸네일 길게**: 첫 화면만이 아니라 페이지 아래(2,200px)까지 축소해 보여 준다. 구성 변형의 차이(표·카드 스타일·구역 리듬·순서)는 첫 화면 밖에 있는 경우가 많다.
- **테마·팔레트 바꿔 보기**: 고른 테마·테마 변형·팔레트·모드가 모든 썸네일과 확대 보기에 적용된다. 54개 테마 × 4,102 조합을 같은 틀에서 비교할 수 있다.

**썸네일이 폰에서도 버벅이지 않는 이유**

- 화면에 보이는 카드(위아래 300px 여유)만 컴파일해 iframe으로 넣고, 벗어나면 iframe을 제거한다.
- 한 번에 하나씩 로드(이전 iframe의 `load`나 700ms를 기다린 뒤 다음), 살아 있는 iframe 상한은 **데스크톱 24 / 터치·좁은 화면 8**.
- 썸네일 문서에서는 스크립트를 걷어 낸다(정적 그림이므로).
- 증거: `e2e/combos.spec.mjs` "…only a few iframes are alive"가 끝까지 훑으며 상한 이내를 확인한다.

**확대 보기(전체 화면 `<dialog>`)**

- 이전/다음(◀ ▶), `←`/`→` 키, 스와이프. 필터가 걸려 있으면 필터 안의 순서로 이동하고 "필터 2/87"을 표시한다. 무작위 이동 버튼.
- **iframe 안에서도** 키보드와 스와이프가 먹는다. 미리보기 문서에 작은 브리지(`postMessage`)를 넣어 방향키와 가로 스와이프를 부모로 전달한다. 가로로 스크롤되는 요소 안에서 시작한 스와이프는 무시하고, 상단 막대와 하단 상태줄 위 스와이프는 별도로 받는다.
- 테마·테마 변형·팔레트·모드·폭(390·768·1280·맞춤)을 바꿔 본다. 폰에서는 "보기 설정" 단추로 접어 둔다. 테마가 금지한 모드(네온·녹턴·게임의 라이트)는 덮어쓰지 않고 이유를 상태줄에 보인다.
- 주소(`/combos/?c=id&theme=&tv=&pal=&mode=`)가 곧 공유 링크다. 열 때 기록을 한 칸만 쌓아 폰의 뒤로 가기가 확대 보기만 닫는다. **ID 복사**, **링크 복사**, **새 창**(`render.html`, 실제 폭으로 전체를 그린다).

**이상함 표시**

- 카드나 확대 보기에서 ⚑ 이상함을 누르면 `localStorage`(`winterholic-static-kit.combo-flags.v1`)에 저장한다. 같은 조합이라도 보기 설정(테마·팔레트·모드)이 다르면 별개 표시다. 확대 보기에서 한 줄 메모를 달 수 있다.
- "이상함 표시" 대화상자: 목록 열기·삭제, **글로 복사**, **.txt 내려받기**, 목록에서만 보기, 모두 지우기(두 번 눌러 확인).
- 내려받는 글 형식(그대로 다음 개선 요청에 붙여 넣을 수 있다):

```
# 이상한 조합 2건 (카탈로그 2.1.0)

- #0005 saas-landing~hero:centered
  SaaS 서비스 소개 · 히어로 가운데 정렬 / 테마 아카데믹 · 다크
  메모: 표가 가로로 넘침
  https://…/combos/?c=saas-landing~hero:centered&theme=academic&mode=dark
```

## 3. 시험하면서 찾아 고친 것

| 결함 | 원인 | 처치 |
|---|---|---|
| 확대 보기에서 테마를 바꿀 때마다 뒤로 가기 기록이 쌓여 Back이 미리보기 안에서 맴돎 | iframe `srcdoc` 교체가 브라우저 세션 기록에 iframe 이동을 남김 | 렌더마다 새 iframe으로 갈아 끼움(`loadViewerFrame`). 시험이 `goBack` 한 번에 확대 보기만 닫히는지 확인 |
| 네온·녹턴·게임에 라이트 모드를 덮어쓰면 `THEME_FORBID`, 오로라 라이트는 `X05` | 모드만 덮어쓰고 테마 금지·축 금지를 보지 않음 | 금지된 모드는 덮어쓰지 않고 이유를 알림, 허용되는 모드는 덮어쓴 뒤 `repairAxes` |
| 토스트가 전체 화면 `<dialog>` 뒤에 가려짐 | 최상위 레이어 순서 | `popover="manual"`로 띄움 |
| 비어 있는 `sandbox` iframe이 Playwright 트레이스 스냅샷에서 콘솔 오류를 냄 | 트레이스가 프레임에 스크립트를 주입 | 썸네일은 스크립트를 걷어 낸 문서에 `sandbox="allow-scripts"`(출처는 격리) |
| 앞 시험이 존재하지 않는 테마 id로 4개 보기를 돌려 사실상 검증이 비었음 | 시험 작성 오류 | 실제 테마 id를 회전시키도록 고침 |

## 4. 검증

| 명령 | 결과 |
|---|---|
| `npm test` | 97 통과(5차 87 + 조합 10) |
| `node scripts/audit.mjs` | `VARIANTS: … 4,102 template×layout compositions.` 통과 |
| `npm run build` + `node scripts/check-generated.mjs` | `REPRODUCIBLE: 2857 generated files match a fresh build byte for byte.` |
| `npx playwright test` | `38 passed (4.1m)` (5차 27 + 조합 11) |
| `node scripts/design-qa/combos-sweep.mjs` | 4,102 조합 × 54 테마(첫 변형 포함 108 보기) = **443,016회 컴파일·검증, 실패 0** (2026-10-21 실행, 약 6분) |

시험이 확인하는 것(`tests/combos.test.mjs`, `e2e/combos.spec.mjs`):

- 열거 수 = 슬롯 곱의 합 = 4,102, id 유일·왕복, `sameAs`는 같은 템플릿의 앞쪽만 가리킴.
- 4,102개 전부가 기본 보기와 회전하는 테마·변형·팔레트·모드 2개 보기에서 컴파일·검증을 통과.
- 필터·검색·정렬 결과가 모델과 일치, 슬롯 필터가 목록을 빈틈없이 나눔.
- 86쪽을 모두 넘기면 4,102 id가 중복 없이 한 번씩 나옴.
- 무작위 40개 조합(시드 고정)을 `render.html`로 전체 렌더, 콘솔 오류 0.
- 확대 보기: 주소 반영, ←→·iframe 안 키보드·스와이프·Esc·Back, 필터 순서 이동, 공유 링크 복원.
- 이상함 표시: 저장·새로 고침 유지·필터·메모·.txt 내보내기·삭제.
- 390px: 한 열, 가로 넘침 없음, 확대 보기가 화면 안.

## 5. 미검증·한계

- Safari/iOS와 실기기의 스와이프, 새 창, `popover`·`<dialog>` 동작은 확인하지 못했다(Chromium 에뮬레이션만).
- 4,102 조합의 미감은 사람이 전수로 보지 않았다. 이 갤러리가 그 작업의 도구다. 컴파일·검증 통과는 "만들어진다"는 뜻일 뿐 "보기 좋다"는 뜻이 아니다.
- 이상함 표시는 브라우저(`localStorage`)에만 있다. 기기를 바꾸거나 저장 공간을 지우면 사라지므로 글로 복사해 두어야 한다.
- 번호는 카탈로그가 바뀌면 달라진다. 기록에는 id를 쓸 것.
- 첫 진입에서 조합 목록을 만드는 데 폰에서 수백 ms가 걸릴 수 있다(데스크톱 Chromium 약 250~400ms 측정).
